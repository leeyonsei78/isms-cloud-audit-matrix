Financial Holdings · AWS + Azure Multi-Cloud

금융 그룹 멀티클라우드 아키텍처

지주사 산하 계열사·자회사가 AWS와 Azure를 함께 사용하는 것을 전제로, 개인신용정보 처리에 따른 망분리(폐쇄망)·Zone 구분·환경 분리(운영/Stage/Test)·회사별 DB 암호화 분리를 반영했습니다. 두 클라우드의 실제 서비스 명칭을 같은 위치에 나란히 배치해 동일 기능을 바로 비교할 수 있도록 구성했습니다.

🚫 인터넷 게이트웨이 없음 — 완전 폐쇄망 회사별 Account/Subscription 분리 운영 · Stage · Test 계정 분리 DB 인스턴스 · 암호화 키 회사별 분리 보안관제(SOC) Zone은 계열사 공통 통합 계열사 공통망(Common Network) 경유 연결 금융보안원 가이드 · 자체 위험평가(CSA) 준수
01 · Classification

Zone과 영역은 무엇으로 나누는가

아래 다이어그램의 모든 경계선은 임의로 그은 것이 아니라, 다음 5가지 기준 중 하나에 대응됩니다. 각 기준이 실제로 어떤 AWS/Azure 단위로 구현되는지 함께 표시했습니다.

기준 1 · 회사 단위
계정 / 구독 경계
계열사·자회사마다 AWS Account / Azure Subscription을 완전히 별도로 발급합니다. 과금·IAM·리소스가 전부 분리되는 가장 상위의 격리 경계입니다.
기준 2 · 환경 단위
운영 · Stage · Test 경계
같은 회사 안에서도 운영(Prod) · Stage · Test 계정을 분리합니다. 운영 계정만 실 개인신용정보를 보유하고, Stage는 마스킹 데이터, Test는 운영 데이터 접근 자체가 차단됩니다.
기준 3 · 업무 계층
Web · WAS · DB Zone 경계
VPC/VNet 내부를 Web → WAS → DB → 관리 4개 Subnet(Zone)으로 나눕니다. 트래픽은 반드시 바로 앞 계층을 거쳐야 하며 계층을 건너뛰는 접근은 차단합니다.
기준 4 · 보안 등급
개인신용정보 처리 여부
개인신용정보를 저장하는 DB Zone은 다른 Zone보다 한 단계 높은 통제(암호화·DAM·별도 보안그룹)를 추가 적용합니다.
기준 5 · 소속
전용(Dedicated) vs 공통(Shared)
인증·관제·백업처럼 전사가 공유해도 되는 기능만 계열사 공통 계정에 두고, 업무 시스템은 회사 전용 계정에만 둡니다.
02 · Architecture

전체 구성도 — AWS · Azure 나란히 비교

03 · Common Network

계열사 공통망 ↔ 계열사망 연결도

계열사망은 서로 직접 연결되지 않습니다. 모든 계열사망은 그룹 공통망(Common Network Zone) 하나만을 거쳐 본사·다른 계열사·인터넷과의 관계를 맺으며, 공통망의 라우팅 테이블 자체에 계열사 간 경로가 존재하지 않도록 구성합니다.

연결 방식
계열사망 ↔ 공통망
계열사별 VPC/VNet은 Transit Gateway Attachment(AWS) / Virtual WAN Hub 연결(Azure) 1개로만 공통망에 연결합니다. 연결 지점에는 방화벽 정책과 허용 포트 화이트리스트를 적용합니다.
차단 원칙
계열사 간 직접 연결 금지
A사 ↔ B사 VPC/VNet Peering은 어떤 경우에도 생성하지 않습니다. 계열사 간 데이터 연계가 필요하면 공통망의 연계 서버(Zone)를 경유하는 승인된 API만 허용합니다.
공통망 보안
공통망 자체도 통제 대상
공통망은 여러 계열사가 드나드는 접점이므로 Network Firewall/Azure Firewall(IPS)을 이중화 배치하고, 공통망 관리 권한은 그룹 통합 보안관제팀만 보유합니다.

05 · Access Control

접근 통제 방안

관리자·운영자는 어떤 경우에도 서버·DB에 직접 접속할 수 없습니다. 반드시 망분리 전용단말 → 그룹 공통 Bastion → 대상 서버 순서를 거치며, DB는 별도로 DAM(DB 접근통제)을 한 번 더 경유합니다.

07 · Network Segmentation

통신 구간 분리 원칙

본사 ↔ 클라우드
전용회선 자체는 클라우드당 1식이지만, 회사별 VIF(AWS) / ExpressRoute Circuit(Azure)로 논리 회선을 나눠 계열사 트래픽을 물리적으로 같은 선로에서도 논리적으로 분리합니다.
Hub ↔ 계열사 VPC/VNet
Transit Gateway / Virtual WAN Hub의 라우팅 테이블에서 계열사 간 상호 라우팅을 차단합니다. A사 트래픽이 B사 VPC/VNet으로 갈 수 있는 경로 자체가 존재하지 않습니다.
회사 내부 3-Tier
Web → WAS → DB 순서로만 통신을 허용합니다. Security Group/NSG 규칙에서 Web→DB 직접 통신, 외부→WAS/DB 직접 통신을 명시적으로 차단합니다.
환경 간 완전 단절
Prod·Stage·Test는 서로 다른 VPC/VNet이며 Peering을 맺지 않습니다. 배포 파이프라인만 계정 경계를 넘나들 수 있고 런타임 트래픽은 넘나들지 않습니다.

09 · Compliance

금융보안원 가이드라인 · 자체 위험평가(CSA) 준수

이 구성도는 「금융분야 클라우드컴퓨팅서비스 이용 가이드」(금융보안원), 전자금융감독규정, 「신용정보의 이용 및 보호에 관한 법률」의 요구를 반영하는 것을 전제로 하며, 실제 이용 전 아래 절차를 순서대로 거쳐야 합니다.

사전 절차 1
내부 정보보호위원회 심의
클라우드 전환 대상 시스템(특히 개인신용정보 처리 시스템)을 그룹 정보보호위원회에서 심의·의결합니다. 본 구성도는 그 심의의 기초 자료로 사용합니다.
사전 절차 2
CSP 보안인증(CSAP) 확인
이용하려는 AWS/Azure 리전·서비스가 클라우드보안인증(CSAP) 등급을 충족하는지 확인하고, 등급이 낮은 서비스는 이용 목록에서 제외하거나 추가 통제를 적용합니다.
사전 절차 3
중요정보처리시스템 해당 여부
전자금융감독규정상 중요정보처리시스템에 해당하면 금융위원회 사전 보고·신고 절차를 이 아키텍처 확정 전에 완료합니다.
사전 절차 4
자체 위험평가(CSA) 실시
이전 전 자체 위험평가(Cloud Security Assessment)를 수행하고 결과를 문서화합니다. 아래 표는 평가 영역과 이 구성도의 반영 여부입니다.

사후관리 1 · 재평가 주기
자체 위험평가는 연 1회 이상, 또는 아키텍처가 실질적으로 변경될 때마다 재실시합니다.
사후관리 2 · 계약상 권리
CSP 계약서에 감사권·데이터 반환권·하도급 현황 통지 의무를 명시적으로 포함시킵니다.
사후관리 3 · 로그 보존
접속기록 등 로그는 전자금융감독규정 기준(통상 2년 이상)에 맞춰 불변 스토리지에 보존합니다.
사후관리 4 · 모의훈련
공통망 SOC 주관으로 연 1회 이상 침해사고 대응 모의훈련을 계열사 합동으로 실시합니다.
본 구성도는 AWS·Azure를 함께 사용하는 금융 그룹의 참고용 아키텍처 예시입니다. 실제 구축 시에는 금융보안원 「금융분야 클라우드컴퓨팅서비스 이용 가이드」, 전자금융감독규정, 「신용정보의 이용 및 보호에 관한 법률」 등 관련 규정과 09장의 자체 위험평가(CSA) 절차를 실제로 수행한 결과를 반영해 조정해야 하며, 특정 3rd-party 보안 제품명은 예시이므로 실제 도입 시 자체 평가를 거쳐 선정하시기 바랍니다. 계열사가 3개사 이상인 경우 계열사 B와 동일한 「전용회선 + 전용 VPC/VNet + Prod·Stage·Test 계정 + 4-Zone」 패턴을 반복 적용합니다.
